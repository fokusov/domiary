# Domiary — план MVP

**Статус:** Draft
**Дата:** 2026-10-02
**Цель:** Domiary v1.0 по [PRD.md](PRD.md) §27 и §40, порядок фаз по [ROADMAP.md](ROADMAP.md).

Этот документ отвечает на вопрос «кто, что и в каком порядке делает». Состав фич здесь не меняется: он задан в PRD и ROADMAP.

---

## 1. Исходные условия

| Параметр | Значение |
|---|---|
| Платформа | 1С:Предприятие 8.5, мобильная платформа (локально установлена 8.5.1) |
| Целевая ОС MVP | **Android-first**. iOS после v1 |
| Команда | Игорь (человек) + три AI-агента: Claude, Codex, GLM-5.3 |
| Время человека | 3–5 часов в неделю |
| Ключевое ограничение | Человек — единственный, кто принимает решения, тестирует на телефоне и публикует. Его время — самый дефицитный ресурс |

Следствие: процесс строится так, чтобы время Игоря уходило только на решения, приёмку на устройстве и реальное использование. Всё остальное делают агенты.

---

## 2. Роли

### Игорь — Product Owner и приёмка

- принимает продуктовые и архитектурные решения (утверждает ADR);
- приоритизирует backlog и режет scope;
- готовит окружение, которое агенты не могут создать сами (SDK, устройство, ключи, аккаунты);
- собирает APK через Сборщик мобильных приложений и ставит на телефон (пока это не автоматизировано);
- проводит приёмку каждого среза на реальном Android-устройстве;
- использует приложение на своих реальных данных (dogfooding) с Фазы 1;
- мержит PR в `main`;
- публикует релизы и всё, что видно снаружи (GitHub Releases, RuStore, сайт).

### Claude — Tech Lead и основной 1С-разработчик

- ведёт архитектуру: черновики ADR, модель метаданных, карта экранов;
- нарезает фазы на срезы и задачи;
- **единственный владелец метаданных**: добавляет объекты, реквизиты, формы, подсистемы (через инструменты unica: `meta-add`, `form-add`, `cf-validate` и т. д.);
- пишет сервисные модули (`DomiaryAssets`, `DomiaryMaintenance` …) и формы;
- интегрирует ветки, собирает конфигурацию, гоняет тесты;
- готовит для Игоря сценарий приёмки каждого среза.

### Codex — независимый ревьюер и автор тестов

- ревьюит каждый PR Claude (кросс-модельное ревью ловит то, что автор не видит);
- пишет unit-тесты на доменную логику **до или независимо от** реализации: рекуррентность, следующий срок обслуживания, статус гарантии, потребление по счётчику, остаток долга, прогресс накоплений, миграции;
- реализует чистую доменную логику без метаданных (расчётные функции в общих модулях);
- пишет скрипты в `tools/`: сборка, выгрузка/загрузка конфигурации, проверки.

### GLM-5.3 — контент, документация, проверка текстов

- пользовательская документация и FAQ;
- тексты интерфейса: подписи, пустые состояния, сообщения об ошибках (PRD §35, ARCHITECTURE §26);
- тестовые и демо-данные (fixtures): типовой дом, квартира, 30–50 вещей;
- ручные чек-листы smoke-тестов по ARCHITECTURE §27.4;
- шаблоны issue и PR, CHANGELOG;
- вторичное ревью UX-текстов на «не похоже на 1С» (PRD §44).

### Правила совместной работы агентов

1. **Метаданные меняет только Claude.** Выгрузка конфигурации в XML содержит общие файлы (`Configuration.xml`, состав подсистем). Параллельные правки метаданных дают конфликты, которые сложно разрешать. Codex и GLM работают с модулями, тестами, `tools/` и документацией.
2. Каждый агент работает в своей ветке или worktree. Одна задача — одна ветка — один PR.
3. Общие правила для всех агентов лежат в `AGENTS.md` (Codex читает его напрямую, `CLAUDE.md` ссылается на него).
4. Задачи ведутся в одном месте (GitHub Issues или Backlog.md — решение на Шаге 0). Агент берёт задачу только с меткой своей роли.
5. Ни один PR не мержится без ревью другой модели и зелёных проверок.

## 3. Цикл одного среза

Каждая фаза делится на вертикальные срезы: один срез = одна законченная пользовательская возможность (например, «создать вещь с фото»).

```text
1. Claude     спецификация среза + задачи            (~30 мин чтения у Игоря, если нужны решения)
2. Codex      тесты на доменную логику среза
3. Claude     метаданные + сервисы + формы
4. Codex      ревью PR Claude; Claude правит
5. GLM        тексты интерфейса, чек-лист приёмки
6. Claude     интеграция, сборка, прогон тестов
7. Игорь      сборка APK, приёмка на телефоне, merge  (~30–60 мин)
```

Бюджет Игоря на неделю:

| Активность | Часы |
|---|---|
| Решения, ответы на вопросы, утверждение ADR | ~1 |
| Сборка APK и приёмка на телефоне | 1–2 |
| Использование на реальных данных, заведение багов | ~1 |
| Merge и разбор вопросов | ~0.5 |

## 4. Шаги

### Шаг 0 — Окружение и процесс (1–2 недели)

**Игорь:**

- [x] установить мобильную платформу 8.5, эмулятор и инструменты сборки;
- [x] создать информационную базу и выгрузить конфигурацию в `src/`;
- [x] подготовить Android-устройство в режиме разработчика;
- [x] выбрать трекер задач: **GitHub Issues** в `fokusov/domiary`;
- [ ] создать keystore для подписи APK и хранить его **вне репозитория** (потеря ключа = нельзя обновить приложение у пользователей);
- [ ] подключить Codex и GLM-5.3 к репозиторию, когда до них дойдёт очередь.

Сборка APK — обязанность Игоря. Локальная проверка: тонкий клиент и эмулятор.

**Claude:**

- [x] `AGENTS.md` с правилами для всех агентов, `CLAUDE.md` со ссылкой на него;
- [x] `.gitignore` и `.gitattributes` для выгрузки 1С;
- [x] черновик ADR-001 (именование);
- [x] задачи Шагов 0–2 в GitHub Issues, включая задания для Codex и GLM;
- [ ] каталоги `tests/` и `tools/` появляются вместе с первыми файлами в них.

**Codex:** скрипты сборки и загрузки конфигурации в `tools/`; базовый CI в GitHub Actions (проверка XML и документации; полная сборка 1С в облачном CI пока не планируется из-за лицензий).

**GLM:** шаблоны issue и PR, метки ролей.

**Выход:** любой агент может взять задачу, сделать ветку и PR; Игорь может собрать APK из `main`.

### Шаг 1 — Технический spike (1 неделя)

Цель — снять самые рискованные вопросы до написания основного кода. Без этого шага архитектура опирается на предположения.

Claude делает минимальное приложение «Hello Domiary», Игорь ставит его на телефон и проверяет:

| Проверка | Закрывает вопрос |
|---|---|
| Сделать фото и сохранить | PRD §42.3, ARCHITECTURE §37.5 (хранение файлов) |
| Локальное уведомление через N минут, переживает перезагрузку телефона | PRD §42.9, ARCHITECTURE §37.7 |
| Выгрузить файл и поделиться им (share sheet) | backup и export |
| Залить 1000 вещей и 200 фото, замерить запуск и поиск | PRD §42.4, NFR производительности |
| Обновить APK поверх старого, данные сохранились | миграции |

**Выход:** короткий отчёт со скриншотами и цифрами в `docs/spike/`.

### Шаг 2 — Фаза 0: решения (1–2 недели)

Claude пишет черновики ADR, Codex ревьюит, **Игорь утверждает**:

| ADR | Вопрос |
|---|---|
| ADR-001 | Префикс имён метаданных и правила именования |
| ADR-002 | Хранение вложений (по итогам spike) |
| ADR-003 | Timeline как регистр (подтверждение) |
| ADR-004 | Формат backup и манифест |
| ADR-005 | Планирование уведомлений и их пересборка |
| ADR-006 | Формат исходников и структура репозитория |
| ADR-007 | Тестовый фреймворк: где и как гоняются тесты доменной логики |
| ADR-008 | Задачи: справочник или документ; гарантия на вещи или регистр |

Плюс решения Игоря по открытым вопросам PRD §42, которые влияют на MVP: валюты (одна или несколько), шифрование в v1, шаблоны обслуживания в MVP (рекомендация: нет).

Параллельно:

- **Claude:** модель метаданных (полный список объектов и реквизитов) и карта экранов в виде ASCII-макетов;
- **Игорь:** утверждает карту экранов. Это главное UX-решение проекта, его стоит прочитать внимательно;
- **Codex:** модуль рекуррентности (ARCHITECTURE §10) с тестами — он нужен почти всем фазам.

**Выход:** ROADMAP Фаза 0 закрыта.

### Шаг 3 — Фаза 1: Дом и вещи (3–4 недели)

Срезы:

1. Объекты недвижимости и дерево мест хранения.
2. Вещь: быстрое создание (только название), затем детали.
3. Фото вещи.
4. Покупка: цена, дата, продавец.
5. Гарантия и документы.
6. История вещи (timeline по вещи).
7. Базовый поиск.

**Приёмка (PRD §40):** пункты 2–7, 16.
**Игорь:** с этой фазы заводит в приложение свои реальные вещи. Найденные неудобства — главный источник задач.

### Шаг 4 — Фаза 2: Обслуживание и напоминания (3 недели)

Срезы: разовые задачи → повторяющиеся задачи → правила обслуживания → выполнение обслуживания с автопереносом срока → локальные уведомления → напоминания об окончании гарантии → dashboard «Требует внимания».

**Приёмка:** пункты 8–10, 15.

### Шаг 5 — Фаза 3: Домашние операции (2–3 недели)

Срезы: счётчики → показания и потребление → регулярные платежи → напоминания об оплате → общий timeline → доработка dashboard.

**Приёмка:** пункты 11, 12, 17.

### Шаг 6 — Фаза 4: Простые финансы (2 недели)

Срезы: счета с ручным остатком → цели накоплений и пополнения → долги и погашения → планируемые покупки.

**Приёмка:** пункты 13, 14.

### Шаг 7 — Фаза 5: Безопасность данных (2–3 недели)

Срезы: backup → restore с защитой от перезаписи → пересборка уведомлений после restore → export CSV/JSON → тесты миграций и обновления APK поверх старой версии → оптимизация поиска.

**Приёмка:** пункты 1, 18–20, плюс полный прогон всех 20 пунктов PRD §40 на чистом устройстве.

### Шаг 8 — Релиз v1.0 (1–2 недели)

- **Claude:** release checklist, сборка релизной версии, проверка лицензий сторонних компонентов (PRD §42.15);
- **GLM:** пользовательская документация, CHANGELOG, тексты для страницы релиза и магазина;
- **Codex:** финальное ревью критичных путей (backup, restore, миграции);
- **Игорь:** подписанный APK, GitHub Release, при желании RuStore, анонс. Все публичные действия делает Игорь.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Ограничения мобильной платформы всплывают поздно | Шаг 1 (spike) до основной разработки |
| Конфликты в XML-выгрузке при параллельной работе агентов | Метаданные меняет только Claude |
| Приёмка на телефоне копится и тормозит всё | Маленькие срезы; один APK на неделю с несколькими срезами |
| Интерфейс выглядит как 1С | Карта экранов утверждается до кода; GLM проверяет тексты; приёмка у Игоря на реальных данных |
| Потеря данных при обновлении | Миграции с версией с первого дня (ARCHITECTURE §18), тест «APK поверх старого» в каждой фазе |
| Потеря ключа подписи | Keystore в двух местах вне репозитория |
| Scope creep | Guardrail PRD §41: новая фича — только через ROADMAP Post-v1 |
