# ADR-004 — Формат резервной копии и восстановление

**Status:** Accepted
**Date:** 2026-10-02
**Decider:** Igor Fokusov

## Context

- PRD §33 и ARCHITECTURE §17: резервная копия — часть ядра, а не утилита. Нужны: создание пользователем, версия формата, проверка целостности, предпросмотр перед восстановлением, миграция старой копии, пересборка уведомлений после восстановления.
- Мобильное приложение 1С не умеет выгружать информационную базу целиком (аналог `.dt`) на устройстве. Копию нужно собирать средствами приложения.
- Spike T-001: на эмуляторе работают выгрузка файла через «Поделиться», сохранение файла и чтение выбранного пользователем файла без разрешения AllFilesAccess.
- Вложения хранятся в базе (ADR-002).

## Decision

### Формат

Один файл `domiary-backup-<дата>.zip`:

```text
manifest.json     формат, версии, дата, количество объектов и вложений, контрольные суммы
data.xml          все объекты и записи регистров, сериализатор XDTO платформы
files/<uuid>      двоичные данные вложений, имя = идентификатор вложения
```

`manifest.json`:

```json
{
  "format": "domiary-backup",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "dataVersion": 1,
  "createdAt": "2026-10-02T12:00:00Z",
  "counts": { "objects": 1234, "attachments": 56 },
  "sha256": { "data.xml": "…", "files": "…" }
}
```

- `data.xml` пишется `СериализаторXDTO` по списку метаданных из модуля `РезервноеКопирование`. Регистр `Хроника` не сохраняется: он перестраивается (ADR-003).
- Если на устройстве не окажется работы с ZIP, копия — один XML-файл с вложениями в base64. Это проверяется первым шагом среза резервного копирования.

### Создание

«Ещё» → «Резервная копия» → «Создать». Файл собирается во временном каталоге и отдаётся пользователю через «Поделиться» или «Сохранить». Дата последней копии записывается в `СостояниеПриложения` и показывается на главной, если копии нет больше 30 дней.

### Восстановление

1. Пользователь выбирает файл.
2. Проверка: формат, `formatVersion`, контрольные суммы. Копия из **более новой** версии приложения не восстанавливается.
3. Предпросмотр: дата копии, количество вещей, задач, документов. Предупреждение: «Текущие данные будут заменены».
4. Явное подтверждение кнопкой «Заменить данные».
5. Перед заменой текущие данные автоматически сохраняются в копию во временный каталог (защита от ошибки, PRD §33).
6. Загрузка в одной транзакции с `ОбменДанными.Загрузка = Истина`.
7. Если `dataVersion` копии старше текущей — `Миграции.ОбновитьДанные()`.
8. `Хроника.Перестроить()` и пересборка уведомлений (ADR-005).

Любая ошибка на шагах 6–8 откатывает транзакцию: данные остаются прежними.

### Выгрузка (export)

Отдельно от копии, для владения данными (PRD §34): CSV по разделам и JSON целиком, со смысловыми именами полей (ARCHITECTURE §19). Формат JSON согласуется с `tests/fixtures/demo-home.json`.

## Alternatives

**Резервная копия ОС (OSBackup).** Включена как дополнительная защита, но пользователь не управляет ею и не может перенести данные. Не заменяет собственную копию.

**JSON вместо XDTO XML.** Читаемее, но требует ручной сериализации каждого объекта и ссылок. XDTO делает это платформой. JSON остаётся форматом выгрузки, не копии.

## Consequences

- Каждый новый объект метаданных добавляется в список модуля `РезервноеКопирование`. Интеграционный тест «копия → восстановление → данные совпадают» обязателен (ADR-007).
- Шифрование копии в v1 нет (ARCHITECTURE §20), формат позволяет добавить его новой `formatVersion`.
