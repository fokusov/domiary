# ADR-007 — Тестирование

**Status:** Accepted (основной вариант подтверждён spike T-012: YAxUnit 25.12)
**Date:** 2026-10-02
**Decider:** Igor Fokusov

## Context

- PRD §36 и ARCHITECTURE §27 требуют тестов на доменную логику и критичные сценарии: повторяемость, сроки обслуживания, гарантии, потребление, долги, накопления, миграции, backup и restore.
- Приложение — конфигурация с назначением «Мобильное приложение». Та же конфигурация открывается в тонком клиенте во временной файловой базе на компьютере: Игорь так проверял spike T-001.
- Платформа 8.5 установлена только локально, облачного CI с 1С нет.
- Часть поведения существует только на устройстве: камера, уведомления, файлы, обновление APK.
- unica умеет запускать тесты YAxUnit (`unica.runtime.execute`, `operation: test`), но совместимость YAxUnit с 8.5 и с конфигурацией мобильного назначения не проверена.

## Decision

Три уровня тестов.

### 1. Unit-тесты доменной логики — YAxUnit на компьютере

- Чистые функции живут в общих модулях с суффиксом `КлиентСервер` (ADR-001). Они не обращаются к базе и не берут текущую дату сами: всё приходит параметрами (AGENTS.md, Code rules).
- Тесты — расширение YAxUnit в `tests/` со своими общими модулями `Тесты_<Модуль>`.
- Запуск: временная база `.build/ib` (ADR-006) + расширение тестов + тонкий клиент в пакетном режиме. Скрипт `tools/run-tests.ps1` возвращает код 0 или 1 и путь к отчёту.
- Один и тот же BSL-код исполняется на мобильном устройстве и в тонком клиенте. Отличия контекста ловит `/CheckModules -MobileAppClient -MobileAppServer` (ADR-006, шаг 5).

**Условие принятия.** До первого теста задача T-012 проверяет, что YAxUnit подключается к конфигурации 8.5 мобильного назначения и запускается в тонком клиенте. Если нет — действует запасной вариант ниже.

**Запасной вариант (без внешних зависимостей).** Тесты — экспортные процедуры в общих модулях `Тесты_<Модуль>` прямо в конфигурации, в отдельной подсистеме, которая не попадает в интерфейс. Внешняя обработка `tests/runner.epf` находит их через метаданные, вызывает и пишет результат в JSON. Запуск: тонкий клиент с ключом `/Execute`. Перед сборкой APK тестовые модули не исключаются, но и не вызываются.

### 2. Интеграционные тесты сценариев — там же

Сценарии ARCHITECTURE §27.2 (создать вещь, выполнить обслуживание, снять показания, backup → restore, миграция) пишутся тем же фреймворком. Они работают с данными в чистой временной базе, которую скрипт пересоздаёт перед прогоном.

### 3. Проверка на устройстве — ручной чек-лист

- Для каждого среза Claude готовит короткий чек-лист приёмки в PR.
- Перед релизом Игорь проходит полный smoke-чек-лист ARCHITECTURE §27.4 на телефоне и эмуляторе. Чек-лист пишет GLM, хранится в `tests/smoke.md`.
- Автоматизация UI на устройстве (Vanessa Automation и аналоги) в v1 не планируется.

### Правила

- Каждая чистая функция получает unit-тесты в том же PR.
- Каждый исправленный баг получает регрессионный тест, если это практично.
- Тесты пишет другая модель, чем реализацию (MVP_PLAN: Codex пишет тесты, Claude — код), где это возможно.
- PR не мержится с красными тестами.

## Alternatives

**Только ручное тестирование.** Не масштабируется на годы истории и миграции данных. Отклонено.

**Vanessa Automation для UI-сценариев.** Тяжело для мобильного интерфейса и одного человека на приёмке. Вернуться после v1.

**Тесты на устройстве.** Нет удобного способа запускать их пакетно и собирать результат. Отклонено для v1.

## Consequences

- Доменная логика пишется так, чтобы её можно было вызвать без формы и без базы: это и требование ARCHITECTURE §2.4.
- Появляется внешняя зависимость YAxUnit (только для разработки, в APK не попадает). Её лицензия и обновление описываются в `tests/README.md` (ARCHITECTURE §34).
- Тесты запускаются только на машине с платформой 8.5. Облачный CI проверяет лишь XML и документацию.
