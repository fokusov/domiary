# ADR-008 — Хранение задач, повторяемости и гарантии

**Status:** Accepted
**Date:** 2026-10-02
**Decider:** Igor Fokusov

## Context

Открытые вопросы ARCHITECTURE §37:

- №10 — задачи: объект-справочник или документ/событие;
- №11 — гарантия: реквизиты вещи или отдельный регистр.

Ограничения:

- задачу нужно создать за несколько секунд (PRD §10), минимум обязательных полей (PRD §3.4);
- повторяющиеся задачи должны хранить историю выполнений (PRD §3.6, ARCHITECTURE §2.6);
- одна модель повторяемости для задач, обслуживания, счётчиков и платежей (ARCHITECTURE §10);
- в v1 у вещи одна гарантия (PRD §8); расширенные гарантии и история гарантий не заявлены.

## Decision

### 1. Задачи

- **Справочник `Задачи`** хранит определение задачи и её текущее состояние: название, связанный объект, срок, приоритет, повторяемость, статус, время напоминания, заметка.
- **Регистр сведений `ВыполненияЗадач`** (независимый, непериодический) хранит историю выполнений: задача, дата выполнения, заметка. Измерения: `Задача`, `Идентификатор` (UUID записи).
- Выполнение задачи — одна операция сервиса `Задачи.ВыполнитьЗадачу`:
  1. запись в `ВыполненияЗадач`;
  2. для повторяющейся — новый срок по модулю повторяемости; для разовой — статус «Выполнена»;
  3. запись в `Хроника` (ADR-003);
  4. всё в одной транзакции; уведомления пересчитываются после фиксации (ARCHITECTURE §25).
- Связанный объект — **составной тип с явным списком**: `Вещи`, `ОбъектыНедвижимости`, `МестаХранения`, `Обязательства`, `ЦелиНакоплений`. Не `ЛюбаяСсылка` (ARCHITECTURE §9).

Документ на каждое выполнение не нужен: у выполнения задачи нет сумм и движений, а мобильному приложению лишний объект не помогает.

### 2. Повторяемость

- **Перечисление `ЕдиницыПовторения`**: `День`, `Неделя`, `Месяц`, `Год`.
- В каждом повторяемом объекте два реквизита: `ЕдиницаПовторения` (пусто = не повторяется) и `КоличествоПовторения` (число > 0).
- Объекты: `Задачи`, `ПравилаОбслуживания`, `Счетчики` (снятие показаний), `Обязательства`.
- Расчёт дат — только общий модуль `ПовторяемостьКлиентСервер` (задача T-008). Значения перечисления совпадают с единицами в этом модуле.

### 3. Гарантия

- **Реквизиты справочника `Вещи`**: `ГарантияНачало`, `ГарантияМесяцев`, `ГарантияОкончание`, `ГарантияПродавец`, `ГарантияСервисныйЦентр`, `ГарантийныйДокумент` (ссылка на `Вложения`).
- `ГарантияОкончание` вычисляется сервисом `Вещи` из начала и срока, но может быть введено вручную (срок неизвестен, есть только дата на чеке).
- Регистр `СостояниеГарантий` (ARCHITECTURE §8.3) в v1 **не создаётся**. Если понадобятся несколько гарантий на вещь или история гарантий, данные мигрируют из реквизитов в регистр.

## Alternatives

**Задача как документ.** Даёт историю «из коробки», но дублирует определение задачи в каждом документе и усложняет быстрое создание. Отклонено.

**Только справочник без истории** (дата последнего выполнения в реквизите). Теряется история повторяющихся задач. Отклонено.

**Повторяемость одной строкой** (`"6M"`) или структурой в хранилище значения. Неудобно в запросах и формах. Отклонено.

**Гарантия в регистре сразу.** Лишний объект и лишняя логика ради сценария, которого нет в v1. Отклонено.

## Consequences

- ARCHITECTURE §37 вопросы №10 и №11 закрыты.
- В ARCHITECTURE §8.3 регистр `СостояниеГарантий` помечается как post-v1.
- Модель метаданных (T-006) использует эти решения.
- Миграция гарантии в регистр — отдельная задача, если она понадобится.
